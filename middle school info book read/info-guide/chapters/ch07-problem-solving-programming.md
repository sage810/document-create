## 중단원 도입 — 생각의 씨앗 심기
(교 140~141쪽, p.248~249)

### 도입 지문
- 요지: 효율적인 알고리즘을 설계하고 프로그램을 작성하면 시간·에너지·컴퓨팅 자원을 절약할 수 있음. 지시문 "학교에서 에어컨 온도가 맞지 않아 불편했던 경험을 생각해 보고 에어컨 문제를 효율적으로 해결할 수 있는 방안에 대해 살펴 보자." (p.248, 교 140쪽)

### 장면 구성 (그림 렌더링으로 확인, 5단계 흐름 ①~⑤)
- **① 문제 상황** (만화 4칸 + 의견 말풍선)
  - 1교시 칸: 학생들이 떨며 "선생님, 추워요~" / 온도계 "현재 온도: 20℃"
  - 2교시 칸: 땀 흘리며 "더워요~" / "현재 온도: 28℃"
  - 5교시 칸: 학생이 교사에게 "에어컨 온도를 자동으로 조절하는 방법을 찾고 싶어요."
  - 4번째 칸: 교사와 학생들 "아하, 우리가 설계해 봅시다."
  - 가운데 "문제 해결의 방법 찾기" 표지 아래 의견 4개: 의견 1 "순서대로 에어컨을 켠다." / 의견 2 "온도 센서를 달아 온도에 따라 가동한다." / 의견 3 "온도와 수업 시간표를 고려해서 가동한다." / 의견 4 "반장이 리모컨으로 미리 조정해 놓는다." (p.248)
- **② 문제를 추상화해 보자**: 삽화(교실 1·교실 2, 에어컨, 온도계 25℃, 시간표에 점심시간·체육 시간 표시) 아래 빈 칸 "초기 상태 | 현재 상태 | 목표 상태 | 핵심 요소". 오른쪽 표 — 입력: "각 반 온도, 시간표, 수업 시간 등" / 처리: "온도에 따라 에어컨 가동 여부 결정", "시간표에 따라 에어컨 가동 여부 결정" / 출력: "모든 교실의 적정한 온도" (p.248)
- **③ 알고리즘을 설계해 보자**: 자연어 + 순서도 두 가지로 제시 — 시작 → 각 반 온도 센서를 통해 수집 → "온도 센서 > 25℃이면 에어컨 가동" / "또는 체육 시간이면 에어컨 가동" / "또는 점심시간 이후이면 에어컨 가동" → 끝. 순서도는 마름모 3개(온도 센서 > 25℃ / 체육 시간 이후인가? / 점심 시간 이후인가?) 각각 예 → 에어컨 가동, 아니요 → 다음 판단. (p.249)
- **④ 프로그래밍을 해 보자**: 말풍선 "설계한 알고리즘대로 프로그래밍을 해 보자.", "이렇게 설계했어요.", "다른 반도 비슷할까요?" (p.249)
- **⑤ 문제 해결**: 말풍선 "이번에 학교 전체의 에어컨 가동 방법을 설계해 볼까요?", "이제 쾌적한 환경에서 공부를 할 수 있겠어요.", "전기를 절약할 수 있는 알고리즘을 추가하려면 어떻게 해야 할까요?", "그래!" (p.249)
- 마지막 질문: **Q "우리 학교에서 프로그램을 만들어 해결하고 싶은 문제는 무엇인가?"** (p.248~249)

### 지도 방안 (p.248~249)
- 생활 속 불편 사례(학교 건물 에어컨 운영)를 중심으로 효율적 해결 방안을 생각하게 함. 계속 틀면 쾌적하지만 전기 낭비 → "모든 학급이 공평하면서도 쾌적한 환경"을 위한 운영 방법을 다양하게 찾게 하고, 앞 단원의 추상화·자동화 과정으로 해결하도록 지도. (p.248)
- 핵심 요소 찾기 안목: 예) 점심 식단 메뉴 정하기의 핵심 요소는 필수 영양소 안배, 전체 열량. 학생들과 의견을 나누며 핵심 요소와 필수 조건을 발견하게 함. (p.248)
- 단계별 지도 (p.249)
  1. 문제 해결 방법 찾기: 에어컨 문제를 설명하고, 전기를 절약하면서 우리 반을 쾌적하게 유지할 방법을 의견으로 내게 함. **교과서 방법을 보기 전에 학생이 먼저 다양한 의견을 발표**하게 유도.
  2. 문제 추상화하기: 문제 추상화 = 상태 정의 + 핵심 요소 찾기 + 입력·처리·출력 정리임을 상기. 우리 학교 상황에 맞게 정리하게 함.
  3. 알고리즘 설계하기: 핵심 요소를 반영한 작동 절차를 생각·발표. 자세히 쓰기보다 핵심 요소를 반영한 알고리즘을 발표하는 수준.
  4. 프로그래밍하기: 직접 실행보다는 **교사가 핵심 알고리즘을 시범**으로 보이거나 간단히 발표하는 정도로 진행.
  5. 문제 해결하기: 원하는 대로 해결되었는지 점검하고, 다른 문제에 적용하거나 문제 범위를 확장할 수 있음을 안내.
- 예시 답안(Q): 급식 순서 정하기, 점심 식단 메뉴 만들기, 운동장(체육관) 사용 시간 정하기, 컴퓨터실 사용 시간 정하기 등. (p.248)

### 지식 플러스 "컴퓨팅 사고력으로 사회 문제 해결하기" (p.249)

- **학습 목표**: "실생활의 문제를 탐색하여 발견하고 프로그래밍으로 해결할 수 있다."
- 수업 형태: 문제 기반 학습, 프로젝트 기반 학습 / 준비물: 교과서, 노트와 필기도구, 컴퓨터
- **도입**
  - "일기 예보를 들었던 경험을 이야기해 본다."
  - "일기 예보의 구성이 어떻게 되어 있는지 발표하도록 한다."
  - 유의점: 교과서 142쪽의 일기 예보(서울 예보 원고)를 예로 경험을 나눔.
- **전개**
  - ➊ 문제 추상화하기: 문제 탐색(문제가 무엇인지 적게 함 — "일기 예보 프로그램 만들기") → 초기·현재·목표 상태와 핵심 요소 적기 → 입력·처리·출력으로 정리.
  - ➋ 알고리즘 설계하기: 엔트리의 날씨 데이터를 이용해 설계 — "일기 예보 지역 입력 받기, 지역명에 따라 기온과 비 올 확률 등 불러오기, 일기 예보 말하기".

  - ➍ 프로그램 실행 및 분석하기: 실행·수정, 발표하고 자신의 프로그램과 비교·분석.

- **정리**: 만든 프로그램 공유 → 어려웠던 점과 개선할 사항 발표. 유의점: 자신의 작품을 성찰할 기회 제공.

### 전개 — 본문 흐름과 핵심 개념
#### 소단원 지도 계획 (p.250)
- 지도상의 유의점: 실생활에서 쉽게 접할 수 있는 문제를 살펴보고 추상화와 자동화로 해결하는 과정을 경험하게 함.
- 프로젝트 단계: 단계 1 문제 추상화하기 → 단계 2 알고리즘 설계하기 → 단계 3 프로그래밍하기 → 단계 4 프로그램 실행 및 분석하기(교과서 본문 표기는 "프로그램 실행 및 디버깅하기"). (p.250~251)

#### 프로젝트 1 일기 예보 프로그램 만들기 (과학 | 국어 | 정보) (교 142~143쪽, p.250~251)
- **[문제 상황]**(교과서): 매일 보도되는 일기 예보는 비슷한 내용과 구성. 기상청 데이터를 활용해 매일 변하는 기온·날씨를 지역별로 예보하는 프로그램을 만들고, "지역을 클릭할 때마다 지역 날씨와 기온이 나타나도록 만들어 보자." (p.250)
- **[문제 상황] 해설**(지도서): 일기 예보는 말의 내용과 구조가 같은 패턴. 기사 작성 프로그램이나 인공지능 모델은 이런 패턴의 말·글을 자동 작성할 수 있음 → 반복되는 일기 예보 패턴을 찾아 프로그램을 만듦. (p.250)
- 지도 목표: 실생활 문제를 탐색·발견해 프로그래밍으로 해결하고, 해결 방식을 설명하며 실천 자세를 내면화. (p.250)
- 지도상의 유의점: 학생 경험을 토대로 제작하게 유도 / 엔트리 날씨 블록은 **확장 → 확장 블록 불러오기 → 날씨** 데이터를 불러와 사용. (p.250)
- **단계 1 문제 추상화하기** (교과서 빈칸 구조)
  - ① "문제가 무엇인지 적어 보기 ( )" — 예시: 일기 예보 프로그램 만들기
  - ② "문제 상태를 정의하고 핵심 요소를 찾아보기" — 예시: 초기: 데이터 없음 / 현재: 기온 데이터 있음 / 목표: 모든 데이터 있음 / 핵심 요소: 지역명, 최저 기온, 최고 기온
  - ③ "문제를 입력, 처리, 출력 형태로 만들어 보기" — 교과서 예: 입력 "지역별 날씨" / 처리 "변수에 지역명 입력" / 출력 "지역별 날씨 말하기". 지도서 예시: 입력 지역명·최저 기온·최고 기온 / 처리 변수에 지역명 넣기, 지역명에 따라 최저·최고 기온 불러오기 / 출력 지역별 날씨, 기온 말하기
  - 지도서 해설: 상태 정의에서는 기온 데이터가 없는 상황과 모두 확보된 상황을 예상하게 함. 입력·처리·출력도 완성된 상태를 예상하고 작성하게 함. (p.250)
- **단계 2 알고리즘 설계하기** (교 142쪽): "일기 예보 프로그램을 만들기 위한 알고리즘을 설계해 보자."
  1. **묻고 기다리기**로 일기 예보 지역을 입력받는다.
  2. 지역명에 대답을 입력한다. → **변수** 지역에 따라 → **조건문**으로 날짜별 기온, 비 올 확률 데이터를 불러온다.
  3. 일기 예보 안내 순서에 따라 말하도록 한다.
  - 지도서 해설: 말하는 부분과 데이터를 불러와 처리하는 부분을 구분해 설계하되 **데이터 처리 부분 설계에 중점**. 말하기 블록은 "~과 ~을 합친 값"을 적절히 활용. 일기 예보 말하기에서 반복되는 부분을 찾아 **모둠별로 일기 예보 대사**를 작성하고, 반복 부분에 어떤 날씨 정보를 말하게 할지 모둠별로 정함. (p.251)
- **단계 3 프로그래밍하기** (교 143쪽, 그림 렌더링으로 확인)
  - ① 날씨 데이터 불러오기: "확장 블록( )을 선택하여 확장 블록 화면을 열어 보자." 확장 블록 창에 '날씨'(기온, 강수량, 미세먼지 농도 등 한국의 날씨 관련 블록, 웨더아이 제공)와 '생활안전 국민행동요령' 카드. 불러온 날씨 관련 명령 블록 예: `오늘▾ 서울▾ 전체▾ 의 날씨가 맑음▾ 인가?`, `현재 서울▾ 전체▾ 의 미세먼지 등급이 좋음▾ 인가?`, `오늘▾ 서울▾ 전체▾ 의 최저기온(℃)▾`, `현재 서울▾ 전체▾ 의 기온(℃)▾`, `오늘▾ 서울▾ 전체▾ 의 00▾ 시 기온`. ("확장 블록은 인터넷이 연결되어 있어야 정상적으로 동작합니다.")
  - ② 프로그램 작성하기: "기온 말하기 코드( )를 작성해 보자." 코드 구조:
    ```
    [시작하기 버튼을 클릭했을 때]
    "날씨를 안내할 지역을 넣으세요." 을(를) 묻고 대답 기다리기
    지역명 를 (대답) (으)로 정하기
    만일 <(지역명 값) = 서울> (이)라면
        ("오늘 서울의 기온은" 과(와) (오늘 서울 전체 의 최저기온(℃)) 과(와) "도 입니다." 를 합치기 를 합치기) 을(를) 2 초 동안 말하기
    만일 <(지역명 값) = 부산> (이)라면
        ("오늘 부산의 기온은" 과(와) (오늘 부산 전체 의 최저기온(℃)) 과(와) "도 입니다." ...) 을(를) 2 초 동안 말하기
    ```
  - ③ 응용하기: "프로그램을 실행해 보고, 다음 블록을 이용하여 다양한 변화를 만들어 보자." 날씨 블록의 드롭다운 항목: 최저기온(℃), 최고기온(℃), 습도(%), 강수량(mm), 강수확률(%). 말풍선 "다양한 변화를 주어 나만의 일기 예보 프로그램을 완성해 보세요."
  - 지도서 해설 — 날씨 확장 블록에서 쓸 수 있는 데이터 (p.251)

    | 항목 | 내용 |
    |---|---|
    | 시기 | 어제, 오늘, 내일, 모레 등 |
    | 시도 | 서울, 경기, 인천, 강원 등 |
    | 시군구 | 시도별 시, 구, 군 |
    | 기온 | 최고 기온, 최저 기온, 습도, 강수량 등 |
    | 날씨 | 맑음, 흐림, 비 등 |
    | 시 | 시간 |
  - 모둠 공동 작업 시 지역별로 일기 예보 스프라이트를 만들고 '나의 보관함'으로 하나의 작품으로 합침(아래 활동 플러스). (p.251)
- **단계 4 프로그램 실행 및 디버깅하기**: "완성된 프로그램을 실행해 보고 잘못된 부분이 있으면 수정한 후 공유해 보자. 또, 나와 친구들이 만든 프로그램을 서로 비교해 보고, 다른 점을 이야기해 보자." 지도서: 오류 수정 또는 새 기능 추가 같은 수정·보완 시도 유도 / 처음 설계대로 구현됐는지 점검하고 **무엇을 배웠는지 기록** / 나만의 평가 점검표로 자기 평가. (p.251)

#### 프로젝트 2 프로그래밍으로 작품 만들기 (미술 | 정보) (교 144~147쪽, p.252~255)
- 교과서 표기: 프로젝트 기반 학습 / 디자인 기반 학습. (p.252)
- **[문제 상황]**(교과서): 보스턴의 한 미술관에 지시서와 그 과정이 그려진 작품이 전시됨. 현대 미술가 **솔 르윗(Sol LeWitt, 1928~2007, 원문 표기 Lewitt)**의 '벽 드로잉 #118(Wall Drawing #118)'. 솔 르윗은 직접 그리지 않고 지시서만 전달. 지시서 내용(그림 속 글): "어떤 쭉 펼쳐진 벽 표면 위에, 연필을 사용해서 50개의 임의의 점을 찍습니다. 점들은 벽 표면에 골고루 분포되어야 합니다. 모든 점들은 직선으로 서로 연결되어야 합니다." 지시: "지금부터 이 지시서를 프로그램으로 만들어 솔 르윗의 벽 드로잉 #118 작품을 그려 보세요." 보조 문장: 솔 르윗의 작품은 컴퓨터를 쓰지 않았지만 코드를 작성하고 그 코드대로 프로그램이 그린 것처럼 보임. (p.252)
- 지도 목표: 과거 개념 미술의 대표 작품에서 컴퓨팅 원리를 발견하고, 프로그래밍과 피지컬 컴퓨팅으로 디지털 작품으로 새롭게 만듦. (p.252)

- **단계 1 문제 추상화하기** (교 145쪽, 빈칸 3개 같은 구조)
  - 지도서 예시: 문제 "점, 선으로 그리는 벽 드로잉 컴퓨터로 그리기" / 초기: 배경만 있는 상태 / 현재: 점이 찍힐 위치와 선을 그을 순서를 정한 상태 / 목표: 지시서대로 작품이 완성된 상태 / 핵심 요소: 임의의 점을 고르게 찍기, 모든 점을 직선으로 서로 연결하기 / 입력: 스페이스키를 누르기 / 처리: 찍을 점의 좌표를 구하기, 선을 그을 순서 정하기 / 출력: 점을 찍고, 선을 그리기 (p.253)
  - 해설: 지시서 추상화 = 컴퓨터가 이해할 필요 없는 부분 제거, 실행에 필요한 내용만 남기기. 예) '연필을 사용'은 무시 가능. 지시서는 사람이 읽고 수행하는 알고리즘과 같음. AI 언어 모델 시대에도 사람의 글을 컴퓨팅 시스템이 이해할 언어·구조로 변환하는 과정이 필요. **"점을 골고루 찍는다는 것"을 컴퓨터가 알아들을 언어·구조로 어떻게 바꿀지** 생각하게 함. 같은 의도·결과라도 사람과 컴퓨팅 시스템에는 다른 구조의 설명이 필요할 수 있음을 의논. (p.253)
- **단계 2 알고리즘 설계하기** (교 145쪽): "추출한 핵심 요소를 바탕으로 알고리즘을 설계해 보자."
  - 1 임의의 점 찍기 — 핵심 요소 분석: 2차원 평면에서 점을 찍으려면 x·y 좌표 필요 / 이전에 찍은 점 위치를 알아야 하므로 여러 값을 차례대로 저장하는 **'리스트'** 사용 / 점은 **'도장 찍기'** 활용. → 알고리즘: 화면상의 임의의 좌표를 구한다 → 현재 x, y 좌푯값을 저장한다 → 현재 좌표에 점을 찍는다.
  - 2 점끼리 직선으로 연결하기 — 핵심 요소 분석: 새 점이 찍힐 때마다 기존 점들과 연결, 기존 점은 리스트에 저장 / 기존 점 개수만큼 반복해 선 그리기 / 선을 그릴 때만 펜 그리기. → 알고리즘: 기존 좌표가 있다면 그 수만큼 반복 → 현재 좌표에서 기존 좌표마다 선을 긋는다.
  - 지도서 Q&A (p.253, 수업 발문으로 그대로 사용 가능)
    - 임의의 점 찍기: Q1 "벽 표면은 어떻게 표현할 수 있을까?" — 2차원 디스플레이 / Q2 "점을 찍기 위해 필요한 것은 무엇일까?" — 점 찍는 명령어와 2차원 좌표 / Q3 "임의의 점에서 "임의"는 어떤 의미일까?" — 무작위, 난수(random). 화면을 벗어나지 않는 범위의 x, y 무작위 값 / Q4 "여러 개의 점의 위치를 어떻게 저장할 수 있을까?" — 리스트
    - 점끼리 연결: Q1 "선을 그리기 위해서는 어떤 정보가 필요할까?" — 시작점과 끝점 / Q2 "모든 점을 서로 직선으로 연결하기 위해서는 어떤 방법이 좋을까?" — 종이에 점 개수를 늘려 가며 직접 선을 그려 보고, 점이 하나씩 늘 때 선 개수가 어떻게 증가하는지 관찰. 방법은 여러 가지이며 교과서는 "점이 하나 추가될 때마다 리스트에 저장한 나머지 점들에 직선을 그리는 방법"을 씀. (종이에 점·선 그리기 예 그림)
- **단계 3 프로그래밍하기** (교 146쪽): "함수를 사용한 프로그램을 작성해 보자." (그림 렌더링으로 확인)
  - ① 임의의 점 찍기 구현 — 엔트리
    ```
    함수 정의하기 [점 찍기]
        x 를 (-230 부터 230 사이의 무작위 수) (으)로 정하기
        y 를 (-130 부터 130 사이의 무작위 수) (으)로 정하기
        x: (x 값) y: (y 값) 위치로 이동하기
        (x 값) 항목을 x자취 에 추가하기
        (y 값) 항목을 y자취 에 추가하기
        도장 찍기
    ```
    스크래치는 같은 구조로 x: -230~230, y: **-160~160** 난수, `x: (x) y: (y)(으)로 이동하기`, x자취·y자취 리스트에 추가, `도장찍기`(펜 확장).
  - ② 점끼리 직선으로 연결하기 구현 — 엔트리
    ```
    함수 정의하기 [점끼리 연결하기]
        i 를 0 (으)로 정하기
        (x자취 항목 수) 번 반복하기
            x: (x 값) y: (y 값) 위치로 이동하기      ← 새 점 위치로 복귀
            i 에 1 만큼 더하기
            그리기 시작하기
            그리기 색을 (회색) (으)로 정하기
            x: (x자취 의 (i 값) 번째 항목) y: (y자취 의 (i 값) 번째 항목) 위치로 이동하기
            그리기 멈추기
    ```
    스크래치: `i을(를) 0로 정하기` → `(x자취의 길이)번 반복하기 { x:(x) y:(y)(으)로 이동하기 / i을(를) 1만큼 바꾸기 / 펜 내리기 / 펜 색깔을 (회색)(으)로 정하기 / x:(x자취 리스트의 (i)번째 항목) y:(y자취 리스트의 (i)번째 항목)(으)로 이동하기 / 펜 올리기 }`
  - ③ 완성하기 — 말풍선 "❶, ❷를 활용하여 프로그램을 작성해 나만의 작품을 만들어 보세요."
    - 엔트리: `[시작하기 버튼을 클릭했을 때] 그리기 굵기를 0.2 (으)로 정하기 → 점 찍기` / `[스페이스▾ 키를 눌렀을 때] 점 찍기 → 점끼리 연결하기`
    - 스크래치: `[깃발 클릭했을 때] 초기화 → 점 찍기` / `[스페이스 키를 눌렀을 때] 점 찍기 → 점끼리 연결하기` / `초기화 정의하기 { 모두 지우기, 펜 굵기를 0.1(으)로 정하기, x자취의 항목을 모두 삭제하기, y자취의 항목을 모두 삭제하기 }`
  - 지도서 해설 (p.254): 점 찍기 함수 — 도장 찍기로 원하는 그림을 화면에 남김(엔트리 오브젝트/스크래치 스프라이트로 점 모양을 그림), x·y 변수와 난수로 화면 안 좌표를 임의로 고름, x자취·y자취 리스트에 저장, 오브젝트를 옮기고 도장 찍기. 점끼리 연결하기 함수 — 새 점이 추가될 때마다 기존 점과 선 연결, 새 점 좌표는 x·y 변수에 있음, 자취 리스트 개수만큼 반복하며 항목을 차례로 고르기 위해 **변수 i** 추가, 현재 점에서 각 항목 점으로 이동하며 직선, **펜 내리기/펜 올리기로 필요한 부분만** 그림.
- **단계 4 프로그램 실행 및 디버깅하기** (교 147쪽): "완성된 프로그램을 실행해 보고 잘못된 부분이 있으면 수정한 후 공유해 보자. 또, 나와 친구들이 만든 프로그램을 비교해 보고, 다른 점을 이야기해 보자."
  - 지도서: 정답이 없으므로 교 144~146쪽에서 확장해 자기만의 벽 드로잉을 만들게 함. 고정된 벽 그림과 달리 동적으로 바뀐 디지털 벽 드로잉의 의미를 대화. **Q "프로그래밍으로 그려진 디지털 벽 드로잉은 어떤 특징을 가지고 있을까?"** — A1 반복하기로 점 개수를 쉽게 늘리거나 줄임 / A2 다양한 굵기와 색으로 선을 바꿈 / A3 정지된 결과물이 아닌 움직이는 작품 / A4 사람과의 상호 작용으로 그려지는 작품. 그림: 외부 소리 크기에 따라 점 개수가 달라지는 벽 드로잉 작품. (p.255)
- **단계 + 피지컬 컴퓨팅 시스템 활용하기** (교 147쪽): 솔 르윗 작품이 정적이라면 컴퓨팅 시스템으로 만든 작품은 동적 — 매번 새롭게 그려지고 상호 작용함. "피지컬 컴퓨팅 시스템을 이용하여 벽 드로잉을 더욱 동적인 작품으로 만들어 보자."
  - 1 "피지컬 컴퓨팅 시스템과 상호 작용하는 방법 생각해 보기" — "피지컬 컴퓨팅 시스템의 입력 장치와 작품이 어떤 방법으로 상호 작용할 수 있을까?" 말풍선 "몸을 움직일 때마다 벽 드로잉의 모양과 색이 바뀌면 어떨까?", "소리를 지를 때마다 새로운 점을 찍고 선을 그리면 어떨까?"
  - 2 "상호 작용하는 벽 드로잉 만들기" — "마이크로비트를 사용하여 다양하게 상호 작용하는 벽 드로잉을 구현해 보자." (그림 렌더링으로 확인)
    - 엔트리: `[시작하기 버튼] 그리기 굵기를 0.2로 정하기 → 점 찍기 → 계속 반복하기 { 만일 <(빛 센서 값) < 5> (이)라면 { 점 찍기, 점끼리 연결하기 } }`
    - 스크래치: `벽 그림 정의하기 { 초기화, 15번 반복하기 { 점 찍기, 점끼리 연결하기 } }` / `[마이크로비트 움직일▾ 때] 벽 그림` / `[마이크로비트 앞쪽▾ 방향으로 기울어졌을 때] 펜 색깔을(를) 10만큼 바꾸기`
  - 지도서 해설 (p.255): 관객이 참여하며 그려지는 미디어 아트 벽 드로잉을 상상하고 마이크로비트로 만듦. **빔 프로젝터**로 크게 보여 주면 효과적.

### 활동
#### 프로젝트 1 "일기 예보 프로그램 만들기" (교 142~143쪽, p.250~251) — 개인 제작(모둠 협력 버전 가능), 엔트리 날씨 확장 블록
- **목표**: 반복되는 일기 예보 패턴을 찾아 지역을 입력하면 그 지역 기온·날씨를 말해 주는 프로그램을 만든다.
- **제시 자료·조건**: 일기 예보 원고, 날씨 지도. 엔트리 확장 블록 '날씨'(인터넷 연결 필요). 입력은 묻고 기다리기, 변수 '지역명', 조건문으로 지역별 분기.
- **단계**: 단계 1 문제 추상화(빈칸 3개) → 단계 2 알고리즘 3줄 → 단계 3 ① 날씨 데이터 불러오기 ② 기온 말하기 코드 ③ 응용하기 → 단계 4 실행·디버깅·공유·비교.
- **예시 답안**: 위 코드 구조(묻고 기다리기 → 지역명 정하기 → 만일 지역명=서울/부산 → 합치기로 문장 만들어 말하기).
- **지도상의 유의점**: 개인별 개발 권장, 날씨 블록 사용법 시범, 지역·기온·날씨를 핵심 요소로 유도, 말하기 블록의 '합치기' 활용, 모둠별 대사 작성. (p.188, p.250~251)
- (제안) 지역이 늘어나면 조건문이 길어지므로, 3-2에서 배운 리스트·함수로 줄이는 방법을 심화 과제로 줄 수 있음. 문제 상황의 "지역을 클릭할 때마다"를 살리려면 지역 이름 오브젝트를 화면에 놓고 "오브젝트를 클릭했을 때"로 바꾸는 변형도 가능.

#### 활동 플러스 "블록형 코딩 도구에서 협력 작품 만들기(온라인 버전)" (p.251) — 모둠, 엔트리
- 텍스트 코딩과 달리 블록형 도구에서 여러 작품을 하나로 합치려면 알고리즘 설계 단계부터 계획이 필요. 예) 지역별 알고리즘을 스프라이트 단위로 나눠 제작 후 합침.
- 단계: ❶ 각자 지역별 날씨를 보도하는 스프라이트를 만든다. ❷ 프로젝트를 모둠원에게 공유한다. ❸ 배경과 장면을 작업한 모둠원이 스프라이트 전체를 합친다 — 다른 모둠원 작품을 열어 **나의 보관함**에 각 블록을 드래그 앤 드롭으로 저장, 저장할 때 지역별 대사 코드를 알아볼 수 있게 이름 수정, 전체 코드 보관 후 캐릭터를 만들고 각 코드를 꺼내 사용.

#### 프로젝트 2 "프로그래밍으로 작품 만들기" (교 144~147쪽, p.252~255) — 개인(토론은 전체), 엔트리 또는 스크래치 + 마이크로비트
- **목표**: 솔 르윗의 지시서를 추상화·알고리즘화해 벽 드로잉 #118을 프로그램으로 그리고, 피지컬 컴퓨팅으로 상호 작용하는 디지털 작품으로 확장한다.
- **제시 자료·조건**: 지시서(50개 임의의 점, 골고루 분포, 모든 점 직선 연결), 작품 사진. 필요한 개념: 2차원 좌표, 난수, 리스트(x자취·y자취), 도장 찍기, 펜(그리기 시작/멈추기), 반복, 함수 정의.
- **단계**: 단계 1 추상화 → 단계 2 두 과정(임의의 점 찍기 / 점끼리 연결하기)별 핵심 요소 분석과 알고리즘 → 단계 3 ① 점 찍기 함수 ② 점끼리 연결하기 함수 ③ 완성하기(스페이스 키마다 점 추가) → 단계 4 실행·디버깅·비교 → 단계 + 마이크로비트 상호 작용.
- **예시 답안**: 위 엔트리/스크래치 코드.
- **지도상의 유의점**: 솔 르윗 작품과 프로그래밍 과정의 유사점 토론 / 정답 없음, 기본 형태 완성 후 자기 표현물로 확장 / 단계별 진행 / 피지컬 컴퓨팅으로 상호 작용 탐색 / 빔 프로젝터 활용. (p.189, p.252~255)
- (제안) 지시서는 "50개" 점이지만 교과서 코드는 스페이스 키를 누를 때마다 1개씩 추가하는 구조. "한 번에 그리기"(활동 플러스 2)의 '번 반복하기'로 50개를 한 번에 그리게 하면 원작과 비교하기 좋음. 점 n개를 모두 연결한 선의 수가 n(n-1)/2개(50개면 1,225개)임을 Q2′ 관찰 활동의 정리로 활용 가능.

#### 활동 플러스 "벽 드로잉 다양한 표현 만들기" (p.254) — 개인, 엔트리/스크래치
- 1 다양한 색과 굵기의 선 사용하기: 현재 코드는 정해진 굵기·한 가지 색. ❶ "선이 점점 굵어지면서 그리도록 만들어 보자." ❷ "선의 색상이 무작위로 바뀌면서 그릴 때와 일정한 규칙으로 변하면서 그릴 때의 차이를 살펴보자." ❸ "소리의 크기를 확인할 수 있는 블록을 이용하여 외부 소리에 따라 선의 굵기나 색이 변하도록 만들어 보자."
- 2 한 번에 그리기: '번 반복하기' 블록으로 원하는 개수의 점으로 된 벽 드로잉을 그림. 스크래치는 **'터보 모드'**로 빠르게 그릴 수 있고, 이를 이용해 소리 같은 외부 입력에 상호 작용하는 디지털 작품을 만들 수 있음.

### 활동지 제작 아이디어 (제안)
1. **우리 학교 문제 추상화 카드**: 도입 — 에어컨 만화 4칸(1교시 20℃/2교시 28℃) 제시 후 "에어컨 온도를 자동으로 조절하는 방법을 찾고 싶어요." 의견 1~4 중 가장 좋은 방법 고르고 이유 쓰기 → 전개 — 초기·현재·목표 상태/핵심 요소/입력·처리·출력 표 채우기, 순서도 완성(마름모 3개 빈칸) → 정리 — "전기를 절약할 수 있는 알고리즘을 추가하려면 어떻게 해야 할까요?"에 한 줄 답, "우리 학교에서 프로그램을 만들어 해결하고 싶은 문제는 무엇인가?" 적기.
2. **일기 예보 대본 → 코드 변환 활동지**: 교과서 예보 원고에서 바뀌는 부분(지역, 날씨, 최저·최고 기온)에 형광펜 표시 → 고정 문장과 데이터 블록을 '합치기'로 연결하는 빈칸 코드 채우기 → 확장 블록 항목표(시기·시도·시군구·기온·날씨·시)에서 2개 골라 대사 추가 → 친구 작품 비교 체크리스트.
3. **지시서를 코드로 — 솔 르윗 벽 드로잉**: 도입 "이것이 작품일까? 아니면, 작품에 대한 설명일까?" 찬반 한 줄 → 지시서 문장마다 "컴퓨터에 필요/불필요" 분류(연필 사용 = 불필요) → Q1~Q4 답 쓰기 → 종이에 점 2·3·4·5개 그리고 선 개수 표 채우기 → 점 찍기·연결하기 함수 블록 순서 맞추기 → "디지털 벽 드로잉은 어떤 특징을 가지고 있을까?" 정리.
4. **센서 미디어 아트 설계지**: 센서(거리·기울기·빛·소리) × 표현 방법(점·선 추가, 색·굵기, 범위) 매칭표를 채우고, 내 작품의 상호 작용 시나리오 3컷 그리기.

## 오개념 · 지도 유의점 모음
- **4단계 틀 반복**: 네 프로젝트 모두 "문제 적기 → 초기/현재/목표 상태·핵심 요소 → 입력/처리/출력 → 알고리즘 → 프로그래밍 → 실행·디버깅"을 같은 빈칸 구조로 반복함. 학생이 상태 정의를 형식적으로 채우지 않도록 "데이터가 없는 상황 vs 모두 확보된 상황"처럼 구체적으로 예상하게 함. (p.250)
- **추상화 = 불필요한 것 버리기**: 지시서의 '연필을 사용'처럼 컴퓨터에 필요 없는 요소를 제거하는 것이 추상화임을 사례로 짚음. 사람과 컴퓨터가 같은 의도라도 다른 구조의 설명이 필요함. (p.253)
- **"임의" = 난수, 단 화면 범위 안**: 난수 범위를 무대 크기에 맞춰야 함(엔트리 x ±230, y ±130 / 스크래치 y ±160). 화면 크기 차이(엔트리 480×270, 스크래치 480×360)를 혼동하지 않게 함. (p.253~254, p.258)
- **펜(붓) 올리기/내리기**: 선을 그릴 때만 그리기 시작하고 이동 후 멈춰야 불필요한 선이 생기지 않음. (p.254)
- **도장 찍기 vs 그리기 시작하기**: 도장 찍기는 오브젝트 모습을 복제해 점을 남기고, 그리기 시작하기는 이동 경로에 선을 남김. 정비례 상황 1·2(점)와 상황 3(선)에서 구분. (p.259)
- **변수 이름 = 수식 속 이름**: 기초 대사량에서 체중(kg)·키(cm)·나이 변수 이름을 공식과 일치시키면 수식 블록 조립 오류가 줄어듦. 성별 조건문(1/2) 분기 안내를 구체적으로. (p.190, p.257)
- **수학 교육과정 수준**: 함수는 중2, 1학년은 정비례·반비례 그래프. "1차 함수"라는 교과서 표현이 1학년에게 낯설 수 있음. (p.258)
- **작품 만들기에는 정답이 없음**: 기본형 완성 후 자기 표현으로 확장하게 하고, 평가도 이를 반영. (p.189, p.252)
- **개인 개발 vs 협력**: 01 일기 예보는 개인 개발 권장(모둠 합치기는 활동 플러스), 02는 역할 분담 팀 프로젝트가 성취기준([9정03-09])의 핵심. (p.188, p.190)
- **데이터 수집 동의**: 친구의 신체 정보는 동의한 경우에만 수집. (p.190, p.257)
- **확장 블록은 인터넷 필요**: 날씨 블록은 인터넷 연결이 있어야 동작. (p.251 그림)
- **교사 시범 범위**: 생각의 씨앗의 에어컨 문제는 직접 코딩보다 교사 시범·발표 수준으로 진행. (p.249)

## 원문 오류 의심
- p.191 차시별 지도 계획(정비례 그래프) ➊ 문제 탐색 괄호가 "(프로그래밍으로 작품 만들기)"로 되어 있음 — 01 프로젝트 2 문구를 그대로 옮긴 것으로 보이며 "(정비례 그래프 그리기 프로그램 만들기)"가 맞을 듯.
- p.248 중단원 지도 계획 표의 교과서 쪽수: 02 융합 문제 해결하기 "148~155쪽"이지만 02 본문은 148~151쪽, 152쪽은 중단원 마무리, 153~155쪽은 대단원 창의·융합 프로젝트. 01도 "140~147쪽"으로 생각의 씨앗(140~141쪽)을 포함함.
- 단계 4 명칭 혼용: 지도서 차시 계획·소단원 지도 계획은 "프로그램 실행 및 분석하기", 교과서 본문은 "프로그램 실행 및 디버깅하기". (p.188~191, p.250~259)
- p.258 텍스트 추출에서 "a≠0"이 "a+0"으로 깨져 있음(그림에서는 ≠). 교과서 알고리즘 문장 "② a≠0이 아닐 때까지 다시 입력받는다."는 이중 부정이라 뜻이 모호함 — 지도서 해설처럼 "0을 입력하면 다시 입력받는다"로 이해하는 것이 맞음.
- p.259 문제 상황 2·3 코드: x를 −240~240으로 돌리지만 y=4x는 엔트리 무대 y 범위(±135)를 대부분 벗어남. 오류라기보다 화면 밖 좌표가 많아 그래프 일부만 보인다는 점을 지도서가 언급하지 않음.
- p.259 문제 상황 3 코드: 변수 a를 만든다고 했지만(지도서 알고리즘 ①) 실제 코드는 a 변수 대신 '대답' 블록을 바로 곱함. 지도서 알고리즘과 코드가 조금 다름.
- p.252 작가 이름 표기 "Sol Lewitt" — 일반 표기는 "Sol LeWitt".
- p.250 지도서 예시 입력·처리·출력(입력에 최저·최고 기온 포함)과 교과서 그림의 입력("지역별 날씨")이 서로 다름. 지역명만 입력받고 기온은 처리 단계에서 불러오는 교과서 알고리즘에 비추면 지도서 예시의 입력 칸 구성은 어색함.
